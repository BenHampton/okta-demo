What is Okta?

Okta is an Identity Provider (IdP). Instead of building your own login system with passwords and user databases, you outsource that complexity to Okta. Your app redirects users to Okta to log in, Okta gives back a secure token (JWT), and your app trusts that token to identify the user.

developer.okta.com · free forever

Do not choose Auth0 Platform Free (that's a different product with different SDKs). After verifying your email, you'll land in the Okta Admin Console.

After signup, note your Okta domain — it looks like https://trial-1234567.okta.com or https://yourname-integrator-1234567.okta.com (the older dev-xxxxxxx format is no longer used for new accounts). You'll use this in every config file. Find it in the top-right corner of the Admin Console.

2b

Configure Okta policies

auth policy · access policy · user activation

New Okta Integrator accounts require several policy configurations that aren't set up by default. Skipping these will result in Policy evaluation failed and access_denied errors when logging in.

Federation Broker Mode

New Okta Integrator accounts use Federation Broker Mode by default — user access is controlled entirely by policies, not manual user assignment. This means every policy below must be configured correctly or logins will fail.

1. Create an Authentication Policy

The default policy requires two factors (MFA) which blocks users during development. Create a simpler one:

  1. Go to Security → Authentication Policies
  2. Click Create Policy
  3. Name it Dev Policy → click Save
  4. Click Add Rule inside the new policy
  5. Name it Allow All
  6. Set "And the user must authenticate with" to Password
  7. Set "When signing in, prompt for" to "If the global session exists, allow the user to authenticate silently through SSO"
  8. Set "Then access is" to Allowed
  9. Click Save — make sure this rule is above the Catch-all Rule

2. Assign the Authentication Policy to your app

  1. Go to Applications → Applications → your app
  2. Click the Sign On tab
  3. Scroll to User authentication → click Edit
  4. Change the policy to your new Dev Policy
  5. Click Save

3. Add an Authorization Server Access Policy

Without this, Okta blocks all token requests — your app will authenticate but never receive a JWT.

  1. Go to Security → API
  2. Click the default Authorization Server
  3. Go to the Access Policies tab
  4. Click Add Policy
  5. Name it Dev Policy
  6. Set "Assign to" to your specific app
  7. Click Create Policy
  8. Click Add Rule
  9. Name it Allow All, leave all defaults
  10. Click Create Rule

4. Activate your test user

New users have a "Pending user action" status until they activate their account.

  1. Go to Directory → People → your test user
  2. If status is Pending → click More Actions → Resend Activation Email
  3. The user clicks the link in the email to activate and set their password
  4. Status should change to Active before attempting to log in
Skip the activation email

For a test user you control, click More Actions → Activate and set the password directly — no email needed.

Production note

The "Password only" policy is fine for local development. In production you should enforce MFA — change the Authentication Policy to require at least 2 factors and ensure users are enrolled in Okta Verify or another authenticator.

5. Add name and userEmail claims to the access token

By default Okta's access token doesn't include name or userEmail — you need to add them as custom claims. Without this your /api/profile/me endpoint will return null for both fields.

  1. Go to Security → API → default Authorization Server
  2. Click the Claims tab
  3. Click Add Claim and fill in:
    — Name: name
    — Include in token type: Access Token
    — Value type: Expression
    — Value: user.displayName
    — Include in: Any scope
    — Click Create
  4. Click Add Claim again and fill in:
    — Name: userEmail
    — Include in token type: Access Token
    — Value type: Expression
    — Value: user.email
    — Include in: Any scope
    — Click Create
Why userEmail instead of email?

The claim name email conflicts with a built-in .NET claim type — even after clearing the inbound claim map, .NET silently drops it. Naming it userEmail avoids the conflict and works reliably with User.FindFirst("userEmail") in the controller.

Log out and back in after adding claims

Existing tokens won't include the new claims — they're only added to newly issued tokens. Log out of your React app and log back in to get a fresh token with name and userEmail populated.

2. Update Program.cs

Wire up JWT Bearer authentication and CORS (so your React app on port 5173 can call the API).

src/api-okta-demo/Program.cs 
using Microsoft.AspNetCore.Authentication.JwtBearer;

var builder = WebApplication.CreateBuilder(args);

// Read Okta config from appsettings.json
var oktaIssuer   = builder.Configuration["Okta:Issuer"]!;
var oktaAudience = builder.Configuration["Okta:Audience"]!;

// Add JWT Bearer authentication
builder.Services
  .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
  .AddJwtBearer(options =>
  {
    options.Authority = oktaIssuer;
    options.Audience  = oktaAudience;
    options.RequireHttpsMetadata = false; // dev only
  });

builder.Services.AddAuthorization();

// Allow React dev server to call the API
builder.Services.AddCors(options =>
  options.AddPolicy("ReactApp", policy =>
    policy.WithOrigins("http://localhost:5173")
          .AllowAnyHeader()
          .AllowAnyMethod()
  )
);

// Required to use controller classes
builder.Services.AddControllers();

var app = builder.Build();

app.UseCors("ReactApp");        // Must come before auth
app.UseAuthentication();
app.UseAuthorization();

// Maps all controller classes and their routes
app.MapControllers();

app.Run();
HTTPS redirect warning

If you see Failed to determine the https port for redirect in your terminal, it means app.UseHttpsRedirection() is still in your file from the default template. Remove that line — it's not needed for local development and will cause confusing redirect issues when calling the API from React or Postman over HTTP.

How JWT validation works

When a request arrives with a Bearer token, .NET calls Okta's JWKS endpoint (auto-discovered from the Issuer URL) to get Okta's public keys. It uses those to verify the token's signature — no database call needed. This is the beauty of JWTs.

Protect API endpoints

[Authorize] attribute

Add a controller that demonstrates both a public and a protected endpoint. Replace the existing WeatherForecastController.cs or create a new file.

src/api-okta-demo/Controllers/ProfileController.cs 
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;

[ApiController]
[Route("/api/profile")]
public class ProfileController : ControllerBase
{
    // Public — anyone can call this
    [HttpGet("public")]
    public IActionResult Public()
        => Ok(new { message = "This is public!" });

    // Protected — requires a valid Okta JWT
    [HttpGet("me")]
    [Authorize]
    public IActionResult GetMe()
    {
        // User.Identity is populated from the JWT claims
        var name  = User.FindFirst("name")?.Value;
        var email = User.FindFirst("userEmail")?.Value;

        return Ok(new {
            message = "You are authenticated!",
            name,
            email
        });
    }
}

Set up routing and login UI

root.tsx · routes · layout shell

Now wire everything together. We'll rename main.tsx to root.tsx, move the routes there, simplify App.tsx to a layout shell, and create a custom RequireAuth component (the Okta SDK's built-in one only works with react-router-dom v5).

Why root.tsx instead of main.tsx?

The Vite default entry point is main.tsx, but we're renaming it to root.tsx to better reflect its purpose — it's the root of the entire app tree, not just a generic entry point. It sets up all global providers (StrictMode, BrowserRouter, Security) and defines the routes. This keeps App.tsx clean as a layout shell rather than a routing file.

Step 2 — Create RequireAuth.tsx

The Okta SDK's built-in SecureRoute only works with react-router-dom v5. Since Vite projects use v6, we write our own protected route wrapper. Create this file:

src/components/RequireAuth.tsx 
import { useEffect } from 'react'
import { useOktaAuth } from '@okta/okta-react'
import { toRelativeUrl } from '@okta/okta-auth-js'
import { Outlet } from 'react-router-dom'
// import { AppLoader } from '~/components/AppLoader/AppLoader'

export const RequiredAuth = () => {
  const { oktaAuth, authState } = useOktaAuth();

  useEffect(() => {
    if (!authState) return;

    if (!authState?.isAuthenticated) {
      const originalUri = toRelativeUrl(window.location.href, window.location.origin)
      oktaAuth.setOriginalUri(originalUri)
      oktaAuth.signInWithRedirect()
    }
  }, [oktaAuth, authState, authState?.isAuthenticated])

  if (!authState || !authState?.isAuthenticated) {
    // return <AppLoader />
    return 'Loading...'
  }

  return (
    <>
      <Outlet />
    </>
  )
}
Why this is better than a simple redirect

toRelativeUrl + setOriginalUri saves where the user was trying to go before being redirected to login. After a successful login, Okta automatically sends them back to that page — so navigating directly to /dashboard while logged out will land them on /dashboard after login, not the home page. The useEffect handles the redirect as a side effect rather than during render, which is the React-correct approach. The commented-out AppLoader is a placeholder — swap 'Loading...' for a spinner component when you're ready.

Create the Home page

src/pages/Home.tsx 
import { useOktaAuth } from '@okta/okta-react'
import { useNavigate } from 'react-router-dom'

export default function Home(): JSX.Element {
  const { oktaAuth, authState } = useOktaAuth();
  const navigate = useNavigate();

  if (!authState) return <p>Loading...</p>;

  const login  = () => oktaAuth.signInWithRedirect();
  const logout = () => oktaAuth.signOut({ postLogoutRedirectUri: window.location.origin });

  return (
    <div>
      <h1>Welcome</h1>
      {authState.isAuthenticated ? (
        <>
          <p>You are logged in!</p>
          <button onClick={() => navigate('/dashboard')}>Go to Dashboard</button>
          <button onClick={logout}>Logout</button>
        </>
      ) : (
        <button onClick={login}>Login with Okta</button>
      )}
    </div>
  )
}

Create the Dashboard page

Dashboard is the protected page that calls the /api/profile/me endpoint on the .NET API. It's a regular React component — the protection comes from RequiredAuth wrapping its route in root.tsx, not from anything inside this file itself.

src/pages/Dashboard.tsx 
import { useState, useEffect } from 'react'
import { useOktaAuth } from '@okta/okta-react'
import { apiBaseUrl } from '../config'

interface ProfileData {
  message: string;
  name: string;
  email: string;
}

export default function Dashboard(): JSX.Element {
  const { authState } = useOktaAuth();
  const [data, setData] = useState<ProfileData | null>(null);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    if (!authState?.accessToken) return;

    const token = authState.accessToken.accessToken;

    fetch(`${apiBaseUrl}/api/profile/me`, {
      headers: {
        Authorization: `Bearer ${token}`
      }
    })
      .then((res) => res.json() as Promise<ProfileData>)
      .then(setData)
      .catch((err: Error) => setError(err.message));
  }, [authState]);

  return (
    <div>
      <h1>Dashboard</h1>
      {error && <p style={{color:'red'}}>Error: {error}</p>}
      {data && (
        <div>
          <p>{data.message}</p>
          <p>Name: {data.name}</p>
          <p>Email: {data.email}</p>
        </div>
      )}
      {!data && !error && <p>Loading profile from API...</p>}
    </div>
  )
}
9

Call the protected .NET API

Bearer token in Authorization header

The Dashboard.tsx you created in Step 8 already contains the API call. Here's how it works:

  1. useOktaAuth() gives access to authState, which holds the access token after login
  2. The token is extracted from authState.accessToken.accessToken — a JWT string
  3. It's sent to the .NET API in the Authorization: Bearer ... header
  4. The .NET API validates the token against Okta's public keys and returns the user's profile
  5. The response is stored in state and rendered on screen
Why not call the API directly from RequiredAuth?

Separation of concerns — RequiredAuth only handles the auth gate. Each page is responsible for fetching its own data. This keeps components focused and makes it easy to add more protected pages later without changing the auth logic.

Troubleshooting

common errors and fixes

401 Unauthorized from .NET API

Fix

Check that the Issuer in appsettings.json exactly matches the Authorization Server issuer in Okta (Security → API). Also confirm the Audience matches — it's case-sensitive. A trailing slash mismatch is a common culprit.

CORS error in browser console

Fix

Make sure app.UseCors("ReactApp") appears in Program.cs before app.UseAuthentication(). Also confirm your React dev server is actually on port 5173.

Redirect URI mismatch error from Okta

Fix

The redirect URI in Okta must exactly match (including http vs https and trailing slash) the URI your app is using. Go to your Okta app settings and confirm http://localhost:5173/login/callback is listed exactly as-is.

Vite running on port 5173, not 3000

Fix

Either update all your redirect URIs and CORS to use 5173, or force Vite to use 3000 by adding to vite.config.js: server: { port: 3000 }

Token audience mismatch

Fix

The access token's aud claim must match the Audience value in your .NET config. The default Authorization Server uses api://default. If you created a custom Authorization Server, it may have a different audience. Check via jwt.io.

Why OAuth2 Resource Server?

Spring Security's OAuth2 Resource Server handles JWT validation automatically — it fetches Okta's public keys, verifies the token signature, checks the issuer and audience, and populates the security context. It's the Spring equivalent of AddJwtBearer in .NET.

package com.example.apioktademo;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.web.cors.CorsConfiguration;
import org.springframework.web.cors.CorsConfigurationSource;
import org.springframework.web.cors.UrlBasedCorsConfigurationSource;

import java.util.List;

@Configuration
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .cors(cors -> cors.configurationSource(corsConfigurationSource()))
            .csrf(csrf -> csrf.disable())
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/profile/public").permitAll()
                .anyRequest().authenticated()
            )
            .oauth2ResourceServer(oauth2 -> oauth2
                .jwt(jwt -> {})
            );

        return http.build();
    }

    @Bean
    public CorsConfigurationSource corsConfigurationSource() {
        CorsConfiguration config = new CorsConfiguration();
        config.setAllowedOrigins(List.of("http://localhost:5173"));
        config.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS"));
        config.setAllowedHeaders(List.of("*"));

        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        source.registerCorsConfiguration("/**", config);
        return source;
    }
}
How this maps to .NET

oauth2ResourceServer().jwt() is the Spring equivalent of AddJwtBearer(). permitAll() is the equivalent of no [Authorize] attribute, and authenticated() is the equivalent of [Authorize].

S4

Create the Profile controller

public + protected endpoints

Create the same public and protected endpoints as the .NET version. Spring Security populates a JwtAuthenticationToken from the validated JWT which you can use to read claims.

src/main/java/com/example/apioktademo/ProfileController.java 
package com.example.apioktademo;

import org.springframework.security.core.annotation.AuthenticationPrincipal;
import org.springframework.security.oauth2.jwt.Jwt;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

import java.util.Map;

@RestController
@RequestMapping("/api/profile")
public class ProfileController {

    // Public — anyone can call this
    @GetMapping("/public")
    public Map<String, String> publicEndpoint() {
        return Map.of("message", "This is public!");
    }

    // Protected — requires a valid Okta JWT
    @GetMapping("/me")
    public Map<String, String> getMe(@AuthenticationPrincipal Jwt jwt) {
        String name      = jwt.getClaimAsString("name");
        String userEmail = jwt.getClaimAsString("userEmail");

        return Map.of(
            "message",   "You are authenticated!",
            "name",      name != null ? name : "",
            "userEmail", userEmail != null ? userEmail : ""
        );
    }
}
@AuthenticationPrincipal Jwt

Spring Security injects the validated JWT directly into your method via @AuthenticationPrincipal Jwt jwt. You then read claims with jwt.getClaimAsString("claimName") — much cleaner than .NET's User.FindFirst() pattern.

Run and test

Start the Spring Boot API:

The API starts on http://localhost:8080. To switch your React app from .NET to Spring Boot, update src/config.ts:

src/config.ts 
export const baseDomainDotnet = import.meta.env.VITE_BASE_DOMAIN_DOTNET as string;
export const baseDomainSpringBoot = import.meta.env.VITE_BASE_DOMAIN_SPRING_BOOT as string;

// Switch here to change backend — no component code changes needed
export const apiBaseUrl = baseDomainSpringBoot;

Test with Postman

  1. GET http://localhost:8080/api/profile/public → should return 200 with no token
  2. GET http://localhost:8080/api/profile/me with no token → should return 401
  3. GET http://localhost:8080/api/profile/me with Authorization: Bearer <token> → should return your name and userEmail
.NET vs Spring Boot — key differences

Spring Boot reads the issuer from application.properties and auto-discovers the JWKS endpoint — no explicit audience configuration needed by default (though you can add it). .NET requires both issuer and audience explicitly. Spring also injects the JWT directly into controller methods via @AuthenticationPrincipal, whereas .NET uses User.FindFirst() on the claims principal.
